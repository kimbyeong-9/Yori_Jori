# 제품 요구사항 정의서 (Product Requirements)

- 문서 버전: v0.1 (초안)
- 작성일: 2026-07-31
- 상태: 검토 필요 (Open Decisions 참조)

## 1. 제품 목표

냉장고에 남은 식재료를 등록한 사용자가 반복 검색 없이 조리 가능한 메뉴를 선택하고,
상세 레시피 확인 → 저장 또는 조리 시작 → 조리 완료까지 이어지도록 한다.

핵심 가치: "내가 가진 재료로 지금 뭘 해먹을 수 있는가"에 대한 의사결정 시간을 줄인다.

## 2. 타겟 사용자

- 자취/1~2인 가구 등 냉장고 재료가 자주 남는 사용자
- 매번 재료를 검색·조합해서 메뉴를 고민하는 데 피로를 느끼는 사용자
- MVP 단계에서는 로그인 없이 세션 단위로 이용하는 사용자를 우선 가정한다 (§6 Open Decision 참조)

## 3. 핵심 사용자 흐름

```
재료 등록 → 냉장고 재료 선택 → 추천 요청 → 추천 목록
   → 레시피 상세 → (저장 | 조리 시작) → 조리 완료
```

각 단계는 [event-taxonomy.md](./event-taxonomy.md)의 이벤트와 1:1 또는 1:N으로 매핑된다.

| 단계 | 화면 | 관련 이벤트 |
|---|---|---|
| 재료 등록 | `/ingredients/new` | `ingredient_search`, `ingredient_added` |
| 냉장고 재료 선택 | `/fridge` | `ingredient_selected`, `freshness_selected` |
| 추천 요청 | `/fridge` → `/recipes` | `recommend_request` |
| 추천 목록 | `/recipes` | `recommendation_impression`, `recipe_click` |
| 레시피 상세 | `/recipes/:id` | `recipe_detail_view` |
| 저장 또는 조리 시작 | `/recipes/:id` | `recipe_save`, `recipe_start` |
| 조리 완료 | `/recipes/:id` (조리 모드) | `recipe_complete` |

## 4. 페이지별 요구사항

### 4.1 `/` HomePage
- 서비스 소개 및 핵심 흐름으로의 진입점(냉장고 보기 / 재료 등록) 제공
- 저장한 레시피, 최근 추천 등 요약 진입점 노출 (MVP 범위는 §5 참조)

### 4.2 `/fridge` FridgePage
- 현재 세션의 냉장고 재료 목록 조회
- 재료 선택(다중 선택) → 추천 요청 트리거
- 재료별 신선도(freshness) 상태 표시/변경
- 재료 등록 페이지로 이동하는 진입점 제공

### 4.3 `/ingredients/new` IngredientAddPage
- 재료 검색(자동완성) 후 냉장고에 추가
- 추가 시 수량/신선도 등 최소 메타데이터 입력
- 마스터 재료 목록에 없는 경우의 처리 방식은 §6 Open Decision

### 4.4 `/recipes` RecipeListPage
- 추천 요청 결과(레시피 카드 목록) 노출
- 각 카드는 보유 재료 매칭률/부족 재료를 표시
- 카드 클릭 시 상세 페이지로 이동

### 4.5 `/recipes/:id` RecipeDetailPage
- 레시피 상세 정보(재료, 조리 단계, 시간, 난이도) 표시
- "저장" 액션: `/saved`에 추가
- "조리 시작" 액션: 조리 모드 진입, 완료 시 `recipe_complete` 발생
- 외부 생성(Gemini) 레시피와 저장된 레시피 모두 동일한 상세 뷰를 사용

### 4.6 `/saved` SavedRecipesPage
- 저장한 레시피 목록 조회
- 상세 페이지로 이동, 저장 취소 가능

## 5. MVP 구현 범위 (In-Scope)

- 세션 기반(비로그인) 재료 등록/조회/삭제
- 신선도 상태 선택 (카테고리형, 예: 신선/보통/임박 — 정확한 값셋은 Open Decision)
- 선택 재료 기반 추천 요청 및 목록 표시
- 레시피 상세 조회, 저장, 조리 시작/완료 플로우
- 위 흐름에 대응하는 이벤트 로깅

## 6. 명시적 제외 범위 (Out-of-Scope)

다음은 이번 MVP 문서 및 이후 백로그에서 **다루지 않는다**. 요청 없이 구현하지 않는다 (CLAUDE.md 규칙 3):

- 회원가입/로그인, 소셜 로그인, 다중 디바이스 계정 동기화
- 레시피 평점/리뷰, 커뮤니티/공유 기능
- 영양 성분 분석, 식단 관리, 쇼핑 리스트 자동 생성
- 푸시/이메일 알림
- 다국어 지원
- 결제/구독
- 오프라인(PWA) 지원
- 냉장고 재료 유통기한의 실제 날짜 기반 자동 알림 (신선도는 상태값 선택으로 한정)

## 7. 비기능 요구사항

- 외부 API(Gemini 등) 실패가 전체 서비스 장애로 이어지지 않아야 한다 (CLAUDE.md 규칙 9) — 타임아웃/재시도/폴백 정책은 architecture.md에서 정의
- 추천 요청은 사용자가 대기 상태를 인지할 수 있도록 응답 시간에 대한 UX 처리가 필요 (로딩 상태) — 목표 응답 시간은 Open Decision
- Gemini 응답은 Pydantic 스키마로 검증 후에만 사용 (CLAUDE.md 규칙 8)

## 8. 결정 필요 항목 (Open Decisions)

아래 항목은 [decision-log.md](./decision-log.md)에 OPEN 상태로 등록되어 있으며, 해당 백로그 착수 전 확정이 필요하다.

1. 신선도(freshness) 값셋과 UI 형태 (카테고리 vs 날짜 입력)
2. 재료 마스터 데이터 소스 및 사용자가 목록에 없는 재료를 등록할 때의 처리
3. 추천 레시피의 출처 (Gemini 실시간 생성 / 사전 구축 DB / 하이브리드) 및 영속화 정책
4. 로그인 없는 세션의 식별/만료 정책
5. 분석 이벤트 수집 방식 (자체 저장 vs 외부 도구 연동)
